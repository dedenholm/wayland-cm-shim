cm-shim summary
What it does

cm-shim lets an app that does its own color management, but doesn't speak the Wayland color management protocol, tell the compositor what color space its pixels are in. Without it, the compositor assumes sRGB and converts accordingly.

Two ways to declare:

Bypass (space = display): tells the compositor the app's pixels are already in the compositor's own preferred space for that surface. The user loads the real display ICC in the app. in theory this should get the compositor to not do any color transforms. the reality is a bit more complicated.
Declare: tells the compositor which space the app renders to. The user sets the matching profile in the app. The space is either bundled (-s adobe_rgb, rec2020_g22, display_p3, and the linear, PQ and HLG variants) or manual (-p <primaries> -t <transfer function>, using the protocol's own names).

Commands:

cm-shim [options] run <app> starts one app through the shim. Only that app is affected.
cm-shim [options] install <app> makes it permanent with a launcher override; uninstall <app> removes it.
install.sh builds the shim and installs it to ~/.local/bin, or to /usr/local/bin via sudo if you choose. It also removes everything again.
Settings come from ~/.config/cm-shim/config or from flags (-s, -p, -t, -i). Flags win, and a color definition is always taken whole from one source.
How it does it
Proxy: the shim opens a private Wayland socket and starts the app with WAYLAND_DISPLAY pointing at it. It forwards all traffic through the wl-proxy Rust library.
Hiding: it hides wp_color_manager_v1 from the app and binds it for itself, at protocol version 1. wl-proxy filters the older frog color protocol automatically.
Per surface: every surface the app creates gets a color management object from the shim.
Bypass: the shim asks the compositor for its preferred description and sets that same object back, untouched. It repeats this whenever the compositor signals a change.
Declare: the shim builds one description from named primaries plus a named transfer function and sets it on every surface.
No color math: the shim holds no colorimetric numbers, reads no ICC files, and only passes protocol names and compositor-owned objects through.
Applying changes: a description only takes effect on a surface commit. After setting one, the shim marks the surface damaged and commits it itself (CM_SHIM_NO_COMMIT=1 disables this).
Teardown: each surface has an alive flag, so late compositor replies can't touch objects the app has already destroyed.
Unsupported settings: if the compositor lacks the protocol, the intent or the space, or rejects the declaration, the app still starts but unmanaged. A notify-send notification and a stderr line say so, once per launch.
Install: the shim copies the app's .desktop file into ~/.local/share/applications/, prefixes every Exec= line, sets DBusActivatable=false, and adds a marker line. Only marked files are ever overwritten or deleted.
Measured results:
Ive Measured display output with a calibrite display pro hl, through spotread.
Declare mode under KDE Plasma: dE 2000 of about 0.1 between the same app managing its own display profile, running under kde without color management, and through cm-shim with either adobe_rgb or rec2020_g22 as intermediary profiles. nomacs image viewersits around 1.4, ive yet to determine why.


Bypass on KWin: dE 1.16 with a luminance shift, so KWin still applies part of its ICC after compositing. Bypass is on the back burner for KWin but may still suit other compositors.

ive also done, and will continue doing some testing, to verify methods of color managing under wayland. so far, letting applications manage colours with kde and hyprland colour management disabled has yielded promising results, i will do a bit of further testing and do a write up off it soon.

Caveats

Scope

Native Wayland only. An app running under Xwayland is undefined behaviour, with no warning.
Single-instance apps hand off to an already running copy, which bypasses the shim (gimp --new-instance avoids this).
Any Wayland protocol that wl-proxy doesn't know disappears for the shimmed app.
An app that could speak the color protocol itself loses that ability, including in unmanaged mode.(one should not run wayland color aware apps under this shim)

Whole window, not just the image

GTK3 and Qt draw the UI and the image into one surface, so the UI is read in the declared space too. It comes out more vivid under wide gamuts, and linear spaces wash it out completely.
Menus, tooltips and cursors are separate surfaces and also get declared. Excluding them was discussed but not implemented.
App windows are 8-bit buffers regardless of monitor depth, so wide spaces have coarser steps and linear spaces band.

Compositor differences

KWin: no ICC files from clients, no custom power curve, and only gamma22, PQ, ext_linear and bt1886 as transfer functions. Standard Display P3 (sRGB curve), HLG and ProPhoto are therefore not declarable there.
Hyprland: only the perceptual intent is advertised. With an ICC loaded, it appears to clip all color-managed content to sRGB, and it reports a D50 white point for the output.
The shim binds protocol version 1, so names that exist only in version 2 are unavailable.

Spaces

rec2020_g22 needs an external ICC in the app (Elle Stone's set). No trusted P3 gamma 2.2 profile was found.
On multi-monitor setups a surface carries one description and the app knows one display profile, so only one screen can be correct.

Install

The launcher override is a snapshot; re-run install after an app update changes its launcher.
Menus may cache entries (kbuildsycoca6, or log out and in).
Flatpak apps are untested.
Launches from a terminal, or via file associations that skip the launcher, bypass the shim.
Launchers contain the binary's absolute path. They go stale if the binary moves, and install.sh flags this.
Notifications need notify-send and a running notification daemon.
